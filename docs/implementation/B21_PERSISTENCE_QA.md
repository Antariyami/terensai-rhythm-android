# ПАРИТМ — B2.1: сессии и база Room (QA contract)

**Статус:** предварительная реализация в `feature/b2-1-persistent-sessions`. Не считать production готовой, пока не пройден реальный тест на Xiaomi 13T Pro / HyperOS.

## Что реализовано

- `SessionRepository` — одна активная сессия на базу, atomic Room transactions для начала/действий/завершения.
- `ProgramSnapshotCodec` v1 — сохраняет *полный неизменяемый* план в JSON внутри `sessions.snapshotJson`. Изменение шаблона не переписывает историю.
- `session_events` — START, PAUSE, RESUME, COMPLETE, SKIP с UUID и защитой от повторной команды. `TimelineEngine` вычисляет фактическое время из событий и текущего `Clock`, UI не хранит собственный таймер.
- Параллельные дорожки GUEST/MASTER сохранились на уровне чистой модели, не удваивают общее время.
- Room SQL хранит `finishedAtMs` отдельно от этапов. Проекция завершённой сессии фиксируется на момент окончания.
- Все действия `start/perform/finish` выполняются через `withTransaction` и IO dispatcher.
- JUnit проверяет арифметику план/факт, статусы и восстановление snapshot. Android Room-инструментальные тесты подготовлены на QA-устройство.

## Как проверить тестовый APK на Xiaomi

1. Установить отдельное приложение **ПАРИТМ B2.1** (пакет `kz.paritm.b21.preview`); B1.1, 0.1 и другие версии не затрагиваются.
2. Приветствие → Выбрать программу → внизу нажать **«Проверка B2.1 · сохранение сессии»**.
3. Создать учебную сессию: программа 15 мин, этап 5 мин (**только пример, не корпоративный стандарт**).
4. Нажать «Начать этап», подождать 10–20 секунд, «Пауза этапа». Запомнить первые символы ID и «сохранённых событий: 2».
5. Android Back, завершить приложение из списка последних, вновь открыть проверку. **ID неизменен, время этапа на паузе неизменно, общее время программы увеличилось**.
6. Нажать «Продолжить», подождать 5 сек, «Завершить этап», затем «Завершить тестовую сессию». Новая учебная сессия может быть создана только после завершения предыдущей.
7. Повторный старт не создаёт вторую запись: Room-транзакция возвращает текущий sessionId.

### Известные ограничения

- Это **технический тестовый экран** (не принятый графический S03/S04): большой красивый план/факт появится в B2.2, фокус — B3.
- Перенос старого SharedPreferences v0.1 в Room не активирован; при отдельном QA applicationId прежние данные автоматически вообще не видны. Архив — этап C, миграция после безопасного cutover.
- Текущее ядро основывается на epoch wall clock и рассчитывает прошедшее время после блокировки/перезапуска в рамках неизменных системных часов. **Ручная смена времени или восстановление времени через сеть** пока требует дополнительной стратегии монотонных отметок и сверки после reboot; нельзя заявлять полную устойчивость к этому сценарию.
- Выпуск QA подписан временным debug-key; последующие QA сборки могут не обновляться поверх него без удаления. Release signing/backup — E.
- `assembleDebugAndroidTest` **собирает Android-тесты, но не запускает их**: выполнение возможно только на эмуляторе или настоящем телефоне.

## Границы следующей работы B2.2

Только после успешного пользовательского QA: экран подготовки сессии и основной ход программы, реальные этапы (длительности для «Танысу» согласуются отдельно), единая шкала план/факт и ожидаемое окончание, плавная замена `MainActivity` на Compose-поток, безопасный импорт истории. Не активировать импорт, пока Java UI продолжает писать SharedPreferences.
