## Изменения и контракты
- **Редактор факта:** нажатие на этап «Единой шкалы программы» → диалог фактического начала/конца (дата+часы Asia/Almaty), причина, история правок. Plan snapshot остаётся неизменным. `stage_fact_corrections` — append-only. Проекция событий основана на `TimelineEngine` + effective факты. Важно: если этап уже связан с S13 WorkEntry, исправление **блокируется** до отдельного синхронизированного сценария во избежание задвоения.
- **Защищённое закрытие:** `⋮ Действия → Завершить всю программу…`, подварианты «Сохранить»/«Прервана», подтверждение; автоматически завершаем только фактически завершённые этапы, остальные помечаем SKIP. `session_closures` хранит outcome/reason, WorkEntry не удаляются. Нельзя закрыть, пока есть RUNNING/PAUSED дополнительные работы.
- **Room v11:** `MIGRATION_10_11` только новые таблицы corrections/closures, `ChecklistRunRow`/работы/сессии не переписываются. Room v1→v11 последовательно, без fallback-to-destructive.
- **Дежурство №008:** шаблон v3 с пятью пунктами «Веера имеются в достаточном количестве», всего 54 пункта; upgrade только нетронутых штатных V1/V2, старые Run snapshots остаются. На странице каждого из любых чек-листов «✓ Всё в норме» (в отдельном подтверждающем диалоге) помечает **только** текущий блок, без автоперехода. Для DUTY пустая температура становится `200` с note `temperature-proposed:<suite>=yes`. Это **не подтверждённое измерение**: в отчёте и UI явная пометка, после ручного ввода реального значения флаг очищается. Не изменять уже введённую температуру.
- **Краткий отчёт**: `DutyReport.renderShort`, мастер, дата, вручную указанное фактическое время прибытия, по каждой парной кратко готовность/температура/инвентарь, без автоматической отправки; детальный отчёт сохранён. Фотоотчёт — отдельная будущая задача.
- **Резервная копия**: «Настройки → Сохранить резервную копию» выполняет SQLite `VACUUM INTO`, `quick_check`, запись через Android SAF в выбранный пользователем файл. Импорт сначала **проверяет копию в staging**, затем требует подтверждение и закрывает процесс. При следующем холодном запуске до открытия Room копия заменяет базу, а старая БД с WAL/SHM остаётся во внутренней rollback-папке. Файл содержит персональные данные; хранить его в доверенном месте.
- Тестовая APK использует отдельный `applicationId=kz.paritm.p28.preview`; прежние установленные QA APK и их БД не удалять, автоматически данные между ID не переносятся.

## Xiaomi QA — обязательное, НЕ заменяется CI
1. Из LIGHT/GRAND/PREMIUM карточки запустить программу и проверить знакомые таймеры. ТАНЫСУ/Своя программа не должны сломаться. GRAND 2×30 мин и 30 минут промежутка.
2. Во время GRAND завершить этап, коснуться его в «Единой шкале», изменить время на фактическое, сравнить «План» и «Факт». Закрыть и открыть приложение — правка с причиной остаётся. Попробовать исправить вновь и проверить историю. Таймер другого этапа не теряется.
3. Выполнить часть программы → ⋮ → «Завершить всю программу» → «Прервана», причина; подтверждение. Убедиться, что незавершённые этапы НЕ записаны как выполненная личная работа; закрытая запись осталась в архиве. При активной дополнительной SPA работа блокируется до её завершения.
4. «Чек-листы → Дежурство»: V3 54 пункта, пять парных, включая отдельные веера; в блоке парной с пустой температурой «Всё в норме» → все 10 галочек, температура 200 как **неподтверждённая**, не переходит дальше; отредактировать температуру на измеренную. Если было 86 — не перезаписывает. Проверить PM1 и сумку.
5. В первой странице дежурства ввести фактический приход, например 10:12; скопировать **краткий** отчёт: мастер, дата, приход, по пяти парным готовность, t° и инвентарь. Старый полный отчёт доступен.
6. Сверить S13/Telegram по завершённым работам: на повторном действии не возникает лишних WorkEntry. Запуск/коррекция без сети, рестарт приложения, пять активных сессий.
7. В «Настройках» создать полную backup-копию в приватную папку. Отдельно на **тестовой** базе проверить импорт и cold-start restore; сравнить число сессий/чек-листов/работ. Не импортировать в рабочую базу без подтверждённого backup и возможности отката. Обязательно проверить прежние Room v10→v11 на контролируемой базе.
8. Проверить доступность после перехода полуночи и в новой установке HyperOS. Отметить выявленные ошибки до приёмки.

## Известные границы
- Stage уже перенесённый в S13 пока нельзя править через корректор: требуется транзакционная синхронизация WorkEntry; не нарушать учёт.
- Нужен отдельный UX корректировки завершённой программы в архивной карточке (в текущей версии редактор из активной шкалы).
- Добавление/перестановка плановых этапов *после начала* остаётся отдельной задачей; «+ Процедура» и «+ Событие» сохранены.
- Не существует автоматической фотосъёмки в чек-листе. Фото — отдельное следующее направление с правилами хранения и приватности.
- CI компилирует Android instrumented-test APK, но не исполняет тесты на Xiaomi; владелец отдельно принимает результат.
- Полная база backup/restore новая функция: **не рекомендовать реальным данным до первого физического восстановления на отдельной QA установке**. Постоянный production signing key не выпущен, main не трогать.
