# ПАРИТМ B2.3 — до пяти программ на одном телефоне

## Границы
Офлайн-итерация для Xiaomi 13T Pro / HyperOS. Отличается от B2.2.1 только многосессионной навигацией и репозиторием. PM1/участие — **B2.4**, дополнительное парение/перестановка этапов и параллельная уборка — **B3.3**, визуальный режим фокуса — **B3.1/3.2**. Не заявлять, что эти функции уже работают.

## Техническая модель
- Максимум **5** незавершённых `SessionRow` на одной локальной Room-базе, атомарная проверка лимита в `database.withTransaction`.
- Каждая сессия хранит **глобально уникальный UUID** в качестве `sessionId`. `requestId` стабилен при повторе одной команды Start; новый осознанный Start использует другой UUID.
- `SessionRepository.activeSessions()` выдаёт активные `SavedSession`. `readById(id)`, `perform(id, stageId)` и `finish(id)` сохраняют изоляцию событий и времени. Старый `active()` остаётся только для совместимости QA B2.1/B2.2, **в B2.3 не использовать его для маршрутизации**.
- Точность времени не зависит от непрерывно работающих фоновых таймеров: UI проецирует события из Room на текущий `Clock`, пока открыт экран — обновляет каждую секунду; после закрытия приложения расчёт восстанавливается из временных меток.
- Room **schema 2**: неразрушающая `MIGRATION_1_2` добавляет `originClientId` (случайный локальный UUID для новых сессий; legacy-local для старых), `localRevision` и `modifiedAtMs`. Любая новая команда увеличивает revision одной сессии, старые события сохраняются.
- Синхронизация между разными устройствами ещё **не разработана**. Эта схема лишь создаёт основу для будущих изменений/согласования конфликтов. Персональные аппаратные ID и координаты не считываются.
- QA Android package `kz.paritm.b23.preview` отдельный от B2.2.1. Поэтому прежние данные **не переедут автоматически**, даже несмотря на наличие миграции внутри Room.

## Ручная проверка B2.3 на Xiaomi
1. Установить отдельную APK B2.3. На главной нажать «Моя смена» или выбрать «Танысу» → «Начать новую программу». Проверить, что открываются карточки и подготовка.
2. Создать **три** программы с разными сьютами из локального списка. В карточках каждой свой ID (скрытый в UI, хранится в Room), название сьюта и показания прошедшего времени.
3. В первой начать встречу; затем нажать «К моей смене», во второй начать встречу и поставить паузу. Вернуться к первой: её время должно увеличиться. Вернуться ко второй: её время этапа не изменилось, но общее время увеличилось.
4. Закрыть приложение через последние задачи, открыть заново → «Моя смена». Все три карточки и состояния этапов должны восстановиться.
5. Создать ещё две программы — всего 5. Кнопка «Новая программа» отключена, шестая **не должна** создаваться.
6. В одной программе завершить или пропустить все этапы, затем «Завершить программу». Она исчезает из **активных** (но остаётся в Room для будущего архива C). Становится доступна новая программа (до 5).
7. Проверить, что ± минут, персональные сьюты и слова «Опережение/Отставание» по-прежнему работают из B2.2.1.

## Ограничения и будущая работа
- Только один телефон, нет фоновых нотификаций и общей синхронизации команды.
- Переключение программ не равно физическому выполнению пяти процедур одним мастером. В B2.4 добавим WorkEntry и предупреждение о пересечении личных работ.
- Пока пилотный маршрут — **Танысу 180 мин**; остальные карточки каталога превью без утверждённых поминутных нормативов.
- Лимит 5 распространяется на незавершённые программы. Завершённые записи не удаляются и смогут открываться в C.
- Android instrumentation `RoomSessionRepositoryTest` и `RoomV1ToV2MigrationTest` **собираются** в CI, но для их выполнения нужен Android эмулятор/телефон. JVM unit tests исполняются на GitHub Actions.
- Ручная смена системных часов, перезагрузка, долговременные синхронизационные конфликты и release key/backup требуют дополнительных проверок до production.
